# 可观测性代码与配置改动说明

## 客户需要修改的业务代码

`src/lib.js` 的原有 `logLine` 是此次唯一修改的业务源码文件，新增 7 行。函数先读取当前 OpenTelemetry 上下文，再在已有 JSON 日志中增加 service、status、message、trace_id、span_id。保留原先 ts、level、msg、ctx 字段，原有调用点继续使用同一函数。

```javascript
const { context, trace } = require('@opentelemetry/api');

function logLine(level, msg, ctx = {}) {
  const span = trace.getSpan(context.active())?.spanContext();
  process.stderr.write(JSON.stringify({
    service: process.env.OTEL_SERVICE_NAME || "ccg-mssql",
    status: level,
    message: msg,
    trace_id: span?.traceId,
    span_id: span?.spanId,
    ts: new Date().toISOString(), level, msg, ctx,
  }) + '\n');
}
```

`trace_id` 用于日志与链路定位，`span_id` 用于定位具体调用。启动日志没有请求上下文时，两个 ID 可以为空。若客户现有日志框架已经支持 OpenTelemetry 日志关联，应在该框架中启用等价配置。

## 通过配置接入的能力

| 能力 | 实施操作 | 应用源码改动 |
| --- | --- | --- |
| Node.js HTTP 与 Express Trace | NODE_OPTIONS 预加载 Beacon | 无需增加请求 Span 埋点 |
| MSSQL SQL Span | 启用 tedious 自动插桩 | 无需修改原查询语句 |
| Node.js 运行时指标 | OTEL_METRICS_EXPORTER=otlp 与 runtime-node 插件 | 无需增加业务指标代码 |
| Nginx Span | 安装兼容 ngx_otel_module，配置 propagate 和 OTLP 接收端 | 通过 Nginx 配置实施 |
| 浏览器 RUM 与会话重放 | Rumable 注入 SDK，配置 applicationId 和隐私策略 | 通过代理配置实施 |
| 主机与进程指标 | DataKit 主机与进程采集器 | 通过采集器配置实施 |
| SQL Server 指标 | DataKit sqlserver 采集器与监控账号 | 通过数据库授权和采集器配置实施 |
| 应用与数据库日志采集 | 指定日志文件、JSON 字段解析及服务标签 | 应用日志 ID 补充采用上述 logLine 改动 |

Nginx 与 Node.js 共享 W3C Trace Context。RUM 在匹配的 Fetch/XHR 请求中加入 traceparent。原项目采用整页 HTML 导航，本次通过浏览器中的 Fetch 请求验证 RUM Resource 与后端 Trace 的关联，截图和报告会标注这个验证入口。

## 日志 指标与链路的关联口径

日志与链路使用同一 trace_id。指标是按时间窗口和维度聚合的数据，使用 service、env、version、host 对齐到链路和日志。OTLP 指标在本次 DataKit 中使用 service_name 标签，APM 和日志使用 service，报告会列出这一字段映射。运行时指标、SQL Server 指标和容器资源通过共同 host 与时间范围定位同一运行环境。

## 部署文件及凭据

observability 目录包含 systemd、Beacon、Nginx、Rumable、DataKit 日志与数据库采集器模板、日志轮转配置和部署说明。prepare-host.py 在目标服务器生成数据库管理员、应用和监控账号的随机凭据，真实密码保存至 /etc/ccg-mssql，配置文件权限为 600。客户从目标空间的 DataKit 安装页面获取 DataWay 地址，从 Web 应用接入代码获取 applicationId。
